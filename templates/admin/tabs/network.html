Managed Tor Service
Automatically start and configure the system tor binary on app launch (requires: apt install tor)
Use 0.0.0.0 to allow remote connections, or specific IP like 192.168.0.1
Country codes for exit nodes. Format: {us} or {us},{gb}. Default: US only
Onion Site (.onion)
Expose this deployment over Tor at a persistent .onion address (requires the Managed Tor Service above). One click generates it and applies it live — no restart. The address survives restarts (Tor keys persist in the data dir).
Second Tor Daemon (load-balancing)
Runs a second tor instance with its own circuit/exit IP (only when Auto-start Tor above is on). The built-in HTTP proxy round-robins across both — exit-IP diversity that dodges per-IP rate limits and geo-blocks. Torrent traffic stays Tor-only (never falls back to direct).
Use a different region than the first daemon for diversity. Default: Canada ({ca}) — geographically close, so minimal latency cost.
Built-in HTTP Proxy (HTTP→SOCKS5)
HTTP proxy that forwards to SOCKS5 (Tor). Replaces Privoxy.
For distributed setup: Set SOCKS5 host to your Tor server's IP. If using built-in Tor, use 127.0.0.1
HTTP Proxy (outbound)
Shared outbound HTTP proxy (e.g. Privoxy → Tor). Used by the built-in torrent client and Nitter feeds, 4chan, and SearX fetches. Required for torrents and Nitter.
Built-in Torrent Client (libtorrent)
All torrent traffic is routed through the HTTP proxy (required)
Leave empty for local. Set URL to forward requests to a remote torrent server. Server-to-server requests use load-balanced header authentication.
Where downloaded torrents are saved (local server only)
Port for incoming peer connections
Push notifications
Only needed when your UnifiedPush distributor (ntfy and friends) is self-hosted on your own network. A push endpoint is a URL this server POSTs to, so LAN addresses are refused by default — on a multi-user node, accepting one would let any account aim it at an internal service. Leave off unless registration fails with bad endpoint.
