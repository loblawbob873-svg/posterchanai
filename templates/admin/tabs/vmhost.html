VM hosting

Clients (web, Android, desktop — even one with only a key and relays) manage VMs from Virtual Machines. Requests are NIP-44-encrypted Nostr events addressed to this node's relay identity; the VM console is noVNC over this node's HTTPS behind a one-use ticket issued over Nostr. Needs libvirt + QEMU/KVM — ./install.sh --vmhost sets it up; see docs/VM_HOSTING.md.

Security: the app user needs the libvirt group, and membership of that group is effectively root on this machine. Only enable this on a node you are willing to trust with that.

Public HTTPS URL blank = clients open the console on the same origin as the relay they reached this host through.

Discovery relays are where this host publishes its public announcement so clients on a DIFFERENT relay (e.g. another node) can find it under Virtual Machines → Find hosts. Set this to the relay your clients use (e.g. wss://relay.poster.place); the announcement still points requests back to this host's own relay. Blank = announce on this node's own relay only.

Who may use it

Admins create, delete and assign VMs. Every admin account of this site that has a linked npub, and this node's own key, is already an admin; list extra npubs here. Users only ever see the VMs assigned to them — they can start, stop, reboot and open the console, nothing else. Assigning a VM to an npub is itself a grant; the list below is for people who should see this host before anything is assigned. Anyone else is silently ignored.

Hypervisor and storage

Disks go in <dir>/<vm-uuid>/; installer ISOs live in <dir>/isos/ — copy them there, or download/upload them from Virtual Machines → a host → ISO library. Clients pick from that list and can never name a path.
