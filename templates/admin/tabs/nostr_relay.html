Built-in Nostr Relay (Web of Trust)
The built-in relay is this app's datastore (settings, users, bots, chats all live in its event store), so it always runs — there is no on/off toggle. It serves NIP-01 in its own thread at /relay on the port below, only accepts/syncs notes from a web of trust, and should be fronted with TLS (e.g. wss://relay.yourdomain/).

    Web of Trust
    On: publishing is gated to the trust set, and the relay runs the trust-graph build, metadata backfill, firehose sync, and NIP-05 serving. Off (e.g. a processing node whose relay is internal): publishing is open and all of that background/cross-node work stops — the relay is a pure local store. Restart after changing.
    One per line (npub or hex). The trust set = these seeds + everyone they follow (depth 1) + your own bots/users. Rebuilt automatically daily.
    Depth 2 adds follows-of-follows; depth 3 adds another hop (much larger again). The graph rebuilds daily.
    How often the full follow-graph crawl runs (at the low-traffic UTC hour). New members are still admitted instantly all day; this only refreshes the friends-of-friends graph. Weekly is plenty for a deep (depth-2/3) graph.
    Depth-3 only: max friends-of-friends to crawl upstream (the most-trusted are kept). The FoF tier can be 30k+; crawling all of them floods upstream relays and pegs the CPU. Lower = safer. 0 = uncapped (not recommended).
    Rebuilds the follow graph from the seeds immediately (otherwise daily). Save seed changes first.
    Pulls each user's full history (profile, notes, contacts, reactions, relay list) from upstream into this relay — makes them resolvable/visible even if not yet reached by the backfill. Accepts one or several npubs/hex, comma- or space-separated, to batch a big sync.

    Distributed compute — share machines over Nostr
    When on, this node joins a shared cluster with the peers below: it runs AI jobs (chat / image / music / video) THEY send over Nostr, and it offloads ITS OWN jobs to THEM (round-robin across itself + peers). Your own users are unaffected — this node still serves them locally / via the IP LB; sharing only adds peer capacity both ways. Restart to apply.
    One peer per line: their npub + the relay URL to reach them on (space-separated). Sharing is MUTUAL — if you list a peer, they may use your GPU AND you may use theirs. Blank = no sharing. (npub-only, no relay = they can use you, but you can't reach them.) Restart to apply.

    Concord (communities)
    A member’s app registers each Concord community it has joined, and this relay keeps a copy of its encrypted messages (opaque gift wraps — this server cannot read them) and forwards members’ posts to the community’s own relays, so phones read only this relay. Connections go out through the proxy’s fallback listener (Tor, then direct) and nowhere else; with the proxy off, nothing is mirrored and the apps read the community relays themselves. Budgeted: 25,000 messages per community, 250,000 in all. On by default; takes effect after a relay restart.
    A Concord / Armada invite link (with its # secret). Every member of this instance is joined to it the next time they open Communities — new accounts included. Someone who leaves it is not re-joined. Given only to signed-in members, never to visitors. Blank = no automatic community.

    PosterChanDB (the relay's event store)

    PosterChanDB is where the relay keeps its events — its only store; there is no database server to run. The settings below apply to the running store within seconds of Save.

    How long new events wait in RAM before being written to disk together. A clean stop (systemd) writes them first; a crash or power loss can lose this window of copies synced from other relays (your own posts are written before the relay answers OK). Default 300. Range 1–3600. Applies within seconds of Save — no restart. How much RAM the database may keep for older events AND its index (the index lives on disk and is cached in RAM up to this). Set it low on a small VPS — the database then reads more from disk and stays within it. 0 = automatic (30% of RAM); it also gives memory back by itself when the machine runs low. Range 0–1048576. Applies within seconds of Save — no restart.

    Memory

    When the machine has less free memory than this, the read cache hands segments back to the OS. 0 = automatic (the larger of 512 MB and 10% of RAM). Range 0–1048576. Applies within seconds of Save — no restart.

    Housekeeping

    Compaction and index snapshots run on their own idle-priority thread. The ceilings below are what keep them from competing with the relay for disk and CPU.

    How often housekeeping looks for work. Default 600. Range 60–86400. Applies within seconds of Save — no restart. (after the current wait)
    A snapshot lets a restart load the indexes instead of replaying the log. It writes only what changed since the last one, and a clean stop always takes one. Longer = less disk writing, more log to replay after a crash. Default 24. Range 0.25–48. Applies within seconds of Save — no restart.
    Rewrites a closed segment's live records to free its disk and RAM. Lower reclaims sooner and writes more. Default 40. Range 10–90. Applies within seconds of Save — no restart.
    Housekeeping writes no faster than this. Default 8. Range 1–1000. Applies within seconds of Save — no restart.
    Housekeeping sleeps enough to stay under this share of one core. Default 10. Range 1–100. Applies within seconds of Save — no restart.
    Housekeeping pauses while the machine is busy. 0 = never wait. Default 0.75. Range 0–16. Applies within seconds of Save — no restart.

    Search index

    After a restart, events whose search words are not indexed yet are worked through in steps of this many. Bigger finishes sooner and holds the store lock longer per step (25 ≈ 8 ms). Default 25. Range 1–2000. Applies within seconds of Save — no restart.
